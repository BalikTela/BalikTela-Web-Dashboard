1 Executive Summary

BalikTelaPH has two connected responsibilities: the mobile application records participation and textile exchange activity; the web dashboard manages, monitors, analyzes and governs the resulting records. Matching means connecting the same canonical records by IDs and agreed field meanings, not copying mobile screen totals into web cards.

The web implementation reads Supabase PostgreSQL through its Express API and converts database snake_case columns into TypeScript camelCase records. It then applies account permissions, selected cohorts and calculations before returning charts and tables. A shared database is necessary but not sufficient: mobile must create linked batches, measurements, transfers and recovery evidence in the structure the web actually reads. [S01-S07]

There are three separate information classes: operational records in Supabase, synthetic operational records deliberately inserted into those same tables, and a separate synthetic predictive dataset generated in the server and exported as bundled artifacts. A live database connection does not make a synthetic record real. Environmental equivalents are disabled, and several values still have explicit or implicit demonstration behavior.

QuestionCurrent answer
Where do headline mass metrics come from?material_batches, transfers, measurements and recovery_records; calculated by server/dashboardAnalytics.ts, not independently typed into each tile.
Where do mobile records match?users.id, material_batches.id, listings.id, match_requests.id, transfers.id and facilities.id, with their referencing columns preserved across clients.
Does every mobile table already feed the dashboard?No. Collection receipts, events, support records and several research tables exist in the contract but are not consumed by current analytics. See Sections 10 and 12.
Is predictive analytics using live mobile history?No. It uses 9,600 generated synthetic observations on a fixed 120-week snapshot, separate from Supabase operational analytics.
Is mobile-to-web updating instantaneous?No. There is server/client caching and no operational-data real-time subscription. A stale mounted page needs a data-fetch trigger.
What is the next integration gate?Agree on identifiers, statuses, stage evidence, geographic vocabulary and denominators; then reconcile one controlled lifecycle end to end.

Review basis: local web source commit 5e21c45, reviewed 18 October 2026. This is an implementation data-lineage report, not a claim that production database contents, deployed functions or the separately maintained mobile application were inspected. No shared data was changed while producing it.

2 End to End Data Flow

StepData movement and responsibility
1 Participant actionA consumer, producer, recycler, NGO or collection operator records a listing, proposal, handover, receipt or recovery operation in the mobile app. An authorized web administrator can also register or govern records.
2 Authorized writeUse the shared governed API, or a separately secured mobile backend/RPC with the same canonical contract and invariants. The mobile implementation route must be confirmed by its developer; the web repo does not establish it.
3 Shared persistencePersist canonical IDs, kilogram weights, evidence stages and timestamps in Supabase public tables. Supabase Auth stores credentials; public.users stores the linked application profile and assigned scope.
4 Web source readSupabaseStore calls get_dashboard_source_snapshot for analytics. If that optimization RPC is absent, it falls back to canonical table reads. Other registry endpoints can read tables directly through the same store. [S03, S06]
5 Translation and joinsCodecs map snake_case to camelCase. Transfers are enriched with flow_events and latest stage-specific measurements; listings can inherit missing material metadata from their linked batch. [S04]
6 Authorization and selectionThe Express API reloads current session/account permissions and selects permitted batches, then applies reporting dates and global filters. Aggregate-only responses suppress individual transaction/stakeholder lists. [S07, S08]
7 Derived dataDashboard builder calculates masses, counts, rates, facility allocations, regional groups and engagement summaries. Report generation reuses the same cohort and aggregation logic. [S02, S12]
8 PresentationReact consumes /api/analytics/dashboard or the relevant registry endpoint. Chart.js renders analytics; Leaflet renders reference geography. Canonical kg are converted to metric tons at the display boundary.

Main operational chain: users + organizations -> material_batches -> listings -> match_requests -> transfers -> measurements + flow_events -> recovery_records + reward_ledger -> scoped API calculations -> web charts, registries and reports. Each arrow is a relationship, not an extra quantity to add.

Independent predictive chain: deterministic synthetic generator -> 9,600 event observations -> 120 weekly aggregates -> chronological training/validation/test -> forecast and selection models -> /api/analytics/predictive -> Advanced Analytics. Supabase operational tables are not an input to this chain today.

3.1 Where the synthetic operational figures originate

The original January-September 2026 fixture is generated in src/data/mockData.ts, not collected from participants. Preset national monthly declared masses range from 19,200 kg in January to 49,300 kg in September. Each month is allocated across four region shares (Metro Manila 48%, Central Visayas 20%, Western Visayas 14%, Davao 18%) and six textile shares. Collection and sorting percentages increase by formula; category-specific reuse/recycling ratios create the outcome masses. These assumptions intentionally create a coherent demonstration trend, not measured regional performance. [S25]

buildOperationalDemo converts those fixture figures into linked SYN- batches, declaration/handover/receipt/validation measurements, listings, accepted proposals, completed transfers, Collection/Sorting recovery balances, flow events and reward entries. Engagement is generated separately from preset monthly active-user totals and formula-based session/submission/action/export summaries. Thus engagement totals are not a count of the small synthetic user registry. The initial Supabase dashboard seed persists the resulting records; the web then calculates cards from those tables. It does not use every legacy mock export as a live frontend fallback. [S15]

October is a separate additive synthetic scenario covering 1-16 October 2026: 24 batches based on September fixture rows, with mass scaled by 1.08 and constrained to coherent collected/sorted/outcome balances. Engagement scales selected September summary counts by 1.03 or 1.08 and uses a 16 October timestamp. It reuses fictional SYN registry records. It is a month-to-date illustration, not a full-month projection or observed October growth. These seeding paths describe intended fixture provenance; they are not a fresh inventory of the deployed database. [S16]

5 Predictive Analytics Data Flow

Advanced Analytics > Predictive is a separate proof of concept. Runtime imports syntheticDataset from the deterministic generator in server/analytics/synthetic.ts; it does not read observations.csv on every request and does not query mobile operational tables. The CSV, manifest, evaluation and dictionary are reproducible exports of that generator. Editing the CSV alone will not change runtime forecasts. [S17-S19, S27]

Output / inputOrigin and computation
Training dataSeed 20261016; 9,600 generated linked declaration/collection/offer-response observations; 80 records per week across four regions and six categories. No real participant identities.
Historical window120 complete Monday-Sunday UTC weeks from 24 June 2024 through 11 October 2026. Four forecast weeks start 12, 19, 26 October and 2 November 2026. Fixed snapshot, not next four weeks relative to each page visit.
Partition84 training weeks / 6,720 records; 18 validation weeks / 1,440 records; 18 test weeks / 1,440 records, chronologically 70/15/15. 9,600 records aggregate to 120 weekly time points.
Weekly collection forecastSum collectedKg per week; compare last value, trailing 8-week mean, trailing 26-week OLS trend and 52-week seasonal naive. Lowest validation MAE chooses the method. Predicted collection is constrained not to exceed declared mass.
Projected textile wasteForecast weekly declaredKg using the same baseline comparison. Means projected platform-declared mass, not all textile waste in the Philippines or a validated national forecast.
Four-week totalsSum four weekly forecasts separately for declared and collected mass. These are not additional independent masses; no total confidence interval is claimed.
Weekly uncertainty bandsPer-horizon 80th percentile absolute validation errors; nominal empirical ranges with actual test coverage reported. Not guaranteed 80% confidence.
MAE / WAPE / bias / coverageMAE = sum absolute errors / predictions; WAPE = sum absolute errors / sum observed mass; bias = mean(predicted - observed); coverage = held-out observations inside displayed ranges / observations.
Recycler selection tendencyCategory-conditioned Beta(1,1) smoothed probability = (selected offers + 1)/(offered observations + 2), using validation-selected 8/13/26/52-week recency. Not individual recycler prediction or a distribution that sums to 100%.
Actual selected shareSelected observations in category / all selected observations in chosen window. Different denominator from category selection probability. Selection is not proof of receipt or recycling.
Selection evaluationLog loss and Brier score on held-out responses, compared with a category-blind pooled baseline. Lower error is better; synthetic success does not establish real-world accuracy.
Scope gatesAt least 600 observations and 104 active weeks per selected region/material scope. Region permissions are enforced. Insufficient scopes return no prediction; these are PoC heuristics, not approved research sufficiency thresholds.
Filter and export behaviorDedicated region/material/history controls, not global operational date filters. History selector changes displayed history only. Export requires separate permission and includes only permitted synthetic rows. Model runs cache in process; no model_runs writes.

Future live-model mapping is a separate task: declaration target from unique batch declarations at registration time; collection target from deduplicated Collection evidence at actual collection time; selection target from eligible resolved proposals, including non-selected outcomes and known decision times. Preserve observation timing and avoid using final outcome fields as predictors available before the decision. First choose whether the live target is a calendar-event series or a registration-cohort series; the current operational charts and synthetic weekly model use different time concepts.

Use the exact enum spelling and case from the PostgreSQL contract. Weight evidence is Estimated / Measured / Verified with capitals; recovery stage is Collection / Sorting / Processing / Recovery / Rejection; transfer status is lowercase. Unknown aliases are not normalized reliably. [S04-S05]

Normal governed transfer sequence: accepted proposal -> Reserved -> handover measurement/event -> Handed over -> receipt measurement/event and variance -> Received -> validation measurement/event -> Validated -> confirmed outcome and completion event -> Completed -> eligible reward ledger entry. Cancellation, rejection and dispute are explicit exceptions, not silent row deletion. [S01, S11]

A completed database status is not sufficient evidence by itself. Current API workflow creates the supporting records, but externally written rows can bypass that workflow. The analytic decoder chooses the latest validation-stage measurement without independently proving verifier authority, measurement status or supersession. Both developers must enforce those conditions in the authorized write path before treating results as verified.

8 Time Filters Units and Refresh

ConcernCurrent rule
Operational reporting clockAsia/Manila calendar dates. Last 30/90 days include today through generation time; custom dates are inclusive; future/reversed/invalid ranges are rejected. Previous comparison is the immediately preceding equal elapsed interval, except YTD uses prior year to equivalent Manila date/time.
Cohort denominatorBatch created_at selects the material cohort. Linked latest outcomes through generation time are used even if completion occurs after the selected historical window. Do not compare a mobile completion-month chart with this registration-month chart without reconciling time basis.
Global material filtersRegion/city, textile category, waste source, pathway, weight status, stakeholder role, producer/recycler search, organization, facility and transaction filters select related batches/transfers. Some filters require related user/recovery records to exist. Waste form is stored and displayed, but is not a global filter today.
Filter exceptionsEngagement uses reporting dates and region/city/access scope only. Listing oversight has its own local filters and all-time listing API load. Offer tab uses its own offer load. Predictive has dedicated fixed-snapshot filters. Administrative master lists are not automatically cohort-filtered.
Canonical massPersist and transmit kilograms in fields ending _kg or Kg. Display metric tons: 1 t = 1,000 kg. A 900 kg record displays as 0.9 t. Never save 0.9 into weight_kg when the intended material is 900 kg.
Other units and roundingPieces/meters/bags/bales remain secondary evidence with no automatic kg conversion. General percentages round to one decimal. Aggregate raw weights before rounding; exports retain up to six decimal places in tons.
Server cachesDashboard source snapshot defaults to 15 seconds; calculated dashboard response defaults to 30 seconds, with actor/filter-aware keys. Successful recognized web API mutations invalidate both. External/mobile direct writes do not trigger this in-process invalidation.
Client cacheDashboard cache is session-scoped with a 30-second freshness test when a load is triggered. Visited pages remain mounted. Same-tab mutations emit baliktela:records-changed and invalidate relevant data; sign-out clears private caches.
Important freshness limitationA TTL is not a timer that refreshes the visible page. No operational real-time subscription or universal periodic data refresh is implemented. A mounted page can remain stale indefinitely until reload, applicable navigation/filter change, midnight key change, or local mutation triggers a fetch.
Authentication checkThe 15-second foreground session check refreshes authorization visibility, not all dashboard datasets. Do not describe it as a 15-second mobile synchronization service.
Reliable comparison procedureWait for server cache expiration or use an authorized invalidation mechanism, reload/requery, and compare identical account scope, filters, batch cohort, unit and as-of timestamp. TTLs are not a guaranteed maximum synchronization latency.

9 Worked Reconciliation Example

Illustrative fixture only, not a production record. Select one source batch in one reporting cohort with declared mass 1,000 kg. It has Collection output 900 kg and Sorting output 850 kg at a facility with 2,000 kg prorated period capacity. Two non-overlapping completed outcomes are Reuse 300 kg and Recycling 450 kg, each supported by validation measurements.

Displayed informationExpected resultWhy
Declared / generated1 t1,000 kg counted once, not once per transfer
Collected / sorted0.9 t / 0.85 tDifferent recovery stages, not additive material
Reused / recycled0.3 t / 0.45 tCompleted outcome weights of distinct material portions
Recovered proxy0.75 t300 + 450 = 750 kg
Overall diversion / circularity75%750 / 1,000 x 100
Category recovery83.3%750 / 900 x 100, assuming one category
Sorting yield88.2%750 / 850 x 100
Residual / recovery gap0.25 tmax(0, 1,000 - 300 - 450)
Facility utilization45%900 intake / 2,000 prorated capacity x 100
Completed transaction count2Two transfers, not five stage quantities or ten events

The total is not 1,000 + 900 + 850 + 300 + 450 kg. Those numbers describe overlapping stages and outcome portions of one original material cohort. Multiple transfers per batch require agreed allocation rules; the current normal API acceptance path reserves a listing and does not provide a complete arbitrary partial/split-batch workflow. The two-outcome illustration explains aggregation, not a promise that mobile can create any split without additional validation.

If previous recovered mass were 600 kg, the mass change would be +25%: (750 - 600)/600. If previous diversion rate were 70%, the rate movement would be +5 percentage points, not +5% relative growth. A missing denominator or missing measurement must not be disguised as a verified zero.
